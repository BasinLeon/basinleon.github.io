D1 queries

Ask the database directly.

Run against the worker's D1. Stages 1–4 are measurable today; the conversation blob column is a planned worker change (see docs/conversation-id.md). Until then, join stage 4 via the intake payload, which already carries conversation_id.

Conversations by source, last 30 days

-- stage 4 by source: which distribution path creates conversations
SELECT
  COALESCE(NULLIF(blob11,''), 'direct') AS source,
  blob2 AS page,
  COUNT(*) AS conversations
FROM leon_site_events
WHERE blob1 = 'Conversion'
  AND blob4 IN ('contact-form-submit', 'diagnostic-email-requested')
  AND timestamp >= NOW() - INTERVAL '30' DAY
GROUP BY source, page
ORDER BY conversations DESC;

Engagement funnel: landing → diagnostic/session CTA → conversation

-- stages 2-4: where the chain breaks
SELECT
  SUM(CASE WHEN blob1='Pageview' AND blob2 IN ('/working-session/','/diagnostic/') THEN 1 ELSE 0 END) AS landing_views,
  SUM(CASE WHEN blob1='Conversion' AND blob4='diagnostic-completed' THEN 1 ELSE 0 END) AS diagnostics_completed,
  SUM(CASE WHEN blob1='Conversion' AND blob4 IN ('contact-form-submit','diagnostic-email-requested') THEN 1 ELSE 0 END) AS conversations
FROM leon_site_events
WHERE timestamp >= NOW() - INTERVAL '30' DAY;

Full journey for one conversation (after the worker stores the id)

-- the bridge query: everything one relationship did, in order
SELECT timestamp, blob1 AS event, blob2 AS page, blob4 AS label, blob11 AS utm_source
FROM leon_site_events
WHERE blob18 = 'conv-20260910-a3f9k2'   -- conversation_id, planned blob column
ORDER BY timestamp ASC;
Reading rules

How to read this without lying to yourself.

Headline numbers

Conversations started. Qualified opportunities. Revenue. If these three are flat, nothing else on this page matters.

Context numbers

Visits by source, landing-page views, scroll depth, reading time. Useful only for diagnosing why a headline number moved.
